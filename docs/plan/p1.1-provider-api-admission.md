## Scope

P1.1 establishes the Provider API admission boundary before any asynchronous
lifecycle behavior is exposed:

- Provider v1 wire DTOs that are independent of `instance`, driver, Gin, and
  backend engine types;
- strict, bounded JSON decoding and Contract projection checks for only the
  document schemas actually referenced by `sandbox-provider-v1.yaml`;
- mTLS-only capability discovery with an admitted control-plane identity;
- closed JWS header and claims validation for protected operations;
- operation, request, and read-descriptor binding, including digest, deadline,
  replay, and fencing admission checks;
- stable transport-level rejection behavior without dispatching runtime work.

## Non-goals

P1.1 does not implement or claim:

- P1.2 asynchronous sandbox lifecycle, reconciliation, or Provider routes that
  dispatch mutations;
- a durable Provider operation ledger, leases, events, retained results, or
  multi-controller coordination;
- changes to the local `/instances` management API or reuse of its wire model;
- runtime mTLS listener configuration in P1.1a;
- JWS verification, digest computation, or token replay persistence in P1.1a;
- driver, Docker, exec, session, snapshot, artifact, usage, or gateway work;
- aggregate lifecycle conformance or external caller end-to-end compatibility,
  multi-tenant safety, deployment readiness, or production readiness.

## Ownership boundary

The calling platform remains authoritative for tenant and user authorization,
WorkOrder and Run state, ProviderRevision selection, desired state, and its
aggregate SandboxOperation ledger. This service accepts an already selected
ProviderRevision and owns only provider-local admission, execution progress,
and evidence. Admission DTOs therefore represent the locked wire protocol; they
do not become local business or persistence models. Backend identifiers, host
paths, raw endpoints, daemon diagnostics, credentials, and secrets never enter
stable Provider responses.

## Slice order

### P1.1a: wire DTO and Contract validation harness

1. Define Provider v1 top-level documents and necessary nested value objects in
   a dedicated `providerapi/v1` package.
2. Add a strict bounded decoder that rejects unknown fields, trailing JSON
   values, and oversized encoded bodies before future application dispatch.
3. Add a compatibility harness that verifies the local lock first, discovers
   the OpenAPI's external Schema projection, and compiles Schemas directly from
   an explicit read-only source root.
4. Validate the matching local fixtures against their locked Schemas, decode
   them into the projected DTOs, re-encode them, and validate the projection.
5. Exercise Schema mismatch plus critical enum and identifier constraints with
   in-memory mutations of local fixtures; do not store derived fixtures.
6. Run the projection suite in CI from the repository Contract tree.

Exit criterion: all 16 top-level JSON document schemas directly referenced by
the locked Provider OpenAPI are accounted for, valid examples round-trip
through separate wire DTOs, and all required negative decoder/Schema cases fail
closed. This is component and projection evidence only.

### P1.1b: mTLS-only capability discovery

Implemented as a separate, default-disabled Provider HTTPS listener exposing
only `GET /v1/capabilities`. The listener requires TLS 1.2 or newer, normal
client certificate verification, and a byte-exact URI SAN match against an
allowlist of fragment-free absolute URI identities; no URI scheme is hard-coded.
Certificate or URI identity admission failure terminates the TLS handshake
before HTTP routing.

An admitted caller receives a raw, immutable Provider v1 capability document
through an application port, with empty `capabilities` and `runtime_profiles`
arrays and at least one required content-addressed snapshot/restore
compatibility profile. That profile is metadata only and does not authorize a
runtime capability. Discovery neither accepts nor requires an operation bearer
token, and all Provider mutation routes remain absent. The bounded design and
acceptance evidence are defined in the
[P1.1b capability discovery plan](p1.1b-capability-discovery.md).

### P1.1c: protected-operation admission

Implement the closed JWS algorithm/header/claim allowlists, ProviderRevision
and caller binding, operation-specific Contract ID and digest-profile binding,
normalized request/read-descriptor digests, deadline and policy-decision time
checks, mutation-JTI replay rejection, and stale-fencing rejection. Admission
must finish before repository or driver access. Route handlers may return a
bounded not-implemented result after successful admission; they must not start
P1.2 lifecycle work.

The detailed slice order, local security decisions, acceptance evidence, and
stop conditions are recorded in the
[P1.1c protected-operation admission plan](p1.1c-protected-operation-admission.md).

### P1.1d: admission release gate

Run the applicable locked Contract security cases for every protected
operation, including substitution, expiry, replay, and stale-fencing matrices.
Record reproducible evidence and close P1.1 only when the architecture release
gate passes. Any lifecycle/conformance cases that require P1.2 remain explicitly
not claimed.

## Contract consumption

Local and CI validation use the repository source root or an explicit source
root through `SANDBOX_RUNTIME_CONTRACT_SOURCE_ROOT`. The harness:

1. loads `compatibility/sandbox-runtime/contract.lock.json`;
2. runs the Git tree, cleanliness, digest, manifest, semantic-rule, fixture,
   and Suite verifier;
3. reads the locked OpenAPI to enumerate its Provider Schema
   references and rejects projection drift;
4. loads only the referenced Schemas and corresponding local fixtures;
5. never writes to the source root or copies its contents into generated code,
   build output, or CI artifacts.

Normal unit tests remain runnable without proprietary inputs. Contract
projection tests skip unless the explicit source root is provided; the CI
Contract job always provides it, so a skip cannot satisfy that gate.

## Failure and rollback

- Lock, tree, cleanliness, or digest failure stops Contract reads and fails CI.
- Missing Schema/example mappings or unexpected OpenAPI projection changes fail
  the projection test; they are reviewed as Contract compatibility changes, not
  patched around locally.
- Invalid input is rejected before application, repository, or driver calls.
- A P1.1a rollback removes the new DTO/harness package and CI projection step;
  it does not require data rollback because this slice adds no routes or state.
- P1.1b/c deployment rollback removes only the new Provider listener/routes or
  selects the previous provider revision for new platform bindings. It must not
  migrate existing runs, mutate caller truth, or delete Provider-local
  evidence.
- If the locked Contract lacks authority for a required status or behavior,
  stop that affected slice and record the gap. Do not invent private protocol.
  The P1.1b empty-request boundary is explicitly authorized by the local
  `GET /v1/capabilities` operation declares no query parameters or request
  body, and its response list explicitly includes `400` and `501`. This
  implementation fail-closes with an empty HTTP `400` without a Provider error
  document or detail, while parser-level `501` remains standard-library
  behavior. The response projection and real-server tests provide the required
  release evidence without expanding the Provider surface.

## P1.1a evidence boundary

Passing P1.1a alone proves that a bounded Go wire projection matches selected
locked Schemas/examples and that its JSON decoder fails closed for the tested
input classes. It does not prove semantic-rule completeness, HTTP routing, mTLS,
token admission, application dispatch, durable idempotency/fencing, lifecycle,
the aggregate lifecycle profile, cross-provider interchangeability,
multi-controller reliability, multi-tenant isolation, deployment, or production
readiness.
