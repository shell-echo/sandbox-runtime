# P1.1 Provider API Admission Plan

Status: P1.1a was merged by PR #6 at repository revision
`255c9277a8b2db053bd43d954efb745e33efadb7`; its PR and post-merge CI gates
passed. P1.1b is implemented and locally validated on its feature branch,

remains open.

closed at repository revision `102f36a6240a4c33892b0ebc25232859b63e334c` with

- Contract tree `87e560f9b38eb291c77e036e6690233570afdf01`;
- Sandbox Provider API `1.0.0` and the `sandbox-core-v1` Suite profile.

Authority is ordered as follows:

1. the locked upstream OpenAPI, JSON Schemas, semantic rules, examples, and
   Conformance Suite;
2. the ownership boundary in ADR 0001 and `docs/architecture.md`;
3. this implementation plan;
4. local implementation details.

The upstream Contract is `LicenseRef-Proprietary`. Tests and compatibility
tools consume it from an explicit read-only checkout only after the local lock
verifier accepts its revision-equivalent Contract tree and clean `contract/`
path. No upstream Contract resource is vendored, generated into, or relicensed
by this MIT repository.

## Scope

P1.1 establishes the Provider API admission boundary before any asynchronous
lifecycle behavior is exposed:

- Provider v1 wire DTOs that are independent of `instance`, driver, Gin, and
  backend engine types;
- strict, bounded JSON decoding and Contract projection checks for only the
  document schemas actually referenced by `sandbox-provider-v1.yaml`;
- mTLS-only capability discovery with an admitted control-plane identity;
- closed JWS header and claims validation for protected operations;
- operation, request, and read-descriptor binding, including digest, deadline,
  replay, and fencing admission checks;
- stable transport-level rejection behavior without dispatching runtime work.

## Non-goals

P1.1 does not implement or claim:

- P1.2 asynchronous sandbox lifecycle, reconciliation, or Provider routes that
  dispatch mutations;
- a durable Provider operation ledger, leases, events, retained results, or
  multi-controller coordination;
- changes to the local `/instances` management API or reuse of its wire model;
- runtime mTLS listener configuration in P1.1a;
- JWS verification, digest computation, or token replay persistence in P1.1a;
- driver, Docker, exec, session, snapshot, artifact, usage, or gateway work;
- `sandbox-core-v1` conformance, Agent Platform end-to-end compatibility,
  multi-tenant safety, deployment readiness, or production readiness.

## Ownership boundary

The Agent Platform remains authoritative for tenant and user authorization,
WorkOrder and Run state, ProviderRevision selection, desired state, and its
aggregate SandboxOperation ledger. This service accepts an already selected
ProviderRevision and owns only provider-local admission, execution progress,
and evidence. Admission DTOs therefore represent the locked wire protocol; they
do not become local business or persistence models. Backend identifiers, host
paths, raw endpoints, daemon diagnostics, credentials, and secrets never enter
stable Provider responses.

## Slice order

### P1.1a: wire DTO and Contract validation harness

1. Define Provider v1 top-level documents and necessary nested value objects in
   a dedicated `providerapi/v1` package.
2. Add a strict bounded decoder that rejects unknown fields, trailing JSON
   values, and oversized encoded bodies before future application dispatch.
3. Add a compatibility harness that verifies the local lock first, discovers
   the OpenAPI's external Schema projection, and compiles Schemas directly from
   an explicit read-only source root.
4. Validate the matching upstream examples against their locked Schemas, decode
   them into the projected DTOs, re-encode them, and validate the projection.
5. Exercise Schema mismatch plus critical enum and identifier constraints with
   in-memory mutations of upstream examples; do not store derived fixtures.
6. Run the projection suite in CI after the locked upstream checkout is ready.

Exit criterion: all 16 top-level JSON document schemas directly referenced by
the locked Provider OpenAPI are accounted for, valid examples round-trip
through separate wire DTOs, and all required negative decoder/Schema cases fail
closed. This is component and projection evidence only.

### P1.1b: mTLS-only capability discovery

Add the separate Provider router and `GET /v1/capabilities` only. Require an
admitted control-plane client certificate, return an immutable capability
document through an application port, enforce response projection, and keep
all mutation routes absent. Do not accept or require an operation bearer token
for discovery.

Implementation sequence:

1. Add an opt-in Provider listener configuration that is separate from
   `server.api`. When enabled, server certificate, private key, client CA,
   allowed client workload identities, and ProviderRevision identity are all
   mandatory. There is no plaintext or authentication-disabled mode.
2. Build a dedicated Provider transport server with TLS 1.3 minimum and
   `RequireAndVerifyClientCert`. Trust is rooted only in the configured client
   CA; operating-system roots and certificate common names do not grant access.
3. Apply a local admission profile requiring exactly one SPIFFE URI SAN on the
   verified leaf certificate and an exact match in the configured allowlist.
   The locked Contract establishes workload-identity admission but does not
   prescribe PKI issuance, registration, rotation, or revocation distribution;
   those remain deployment and Agent Platform integration boundaries.
4. Add an application capability service that returns defensive copies of one
   immutable revision document. Its model is independent of HTTP, Gin,
   `instance`, repositories, and runtime-driver structs.
5. Project the application model explicitly into `providerapi/v1.Capabilities`
   and return the raw Contract document with `application/json`, without the
   local management API response envelope. Keep capability and runtime-profile
   advertisements empty while their Provider API behaviors are absent. The
   required content-addressed snapshot profile metadata does not authorize
   restore without a matching advertised capability and Platform
   CompatibilityDecision.
6. Register only `GET /v1/capabilities`. Authenticated requests to mutation or
   lifecycle paths remain 404/405 and cannot reach an application repository or
   driver. Capability discovery succeeds without an Authorization header; a
   bearer value never substitutes for mTLS identity.
7. Validate the emitted response against the locked capability Schema from an
   explicit read-only Contract source, and add real TLS process tests for
   trusted, missing, untrusted, expired, ambiguous, and unadmitted client
   certificates.

Exit criterion: an enabled Provider listener fails closed on incomplete TLS or
identity configuration, only an allowlisted verified client identity receives
the immutable Schema-valid capability document, bearer-only access fails before
dispatch, no mutation route exists, and the local `/instances` listener remains
behaviorally separate. This is mTLS discovery component evidence only.

### P1.1c: protected-operation admission

Implement the closed JWS algorithm/header/claim allowlists, ProviderRevision
and caller binding, operation-specific Contract ID and digest-profile binding,
normalized request/read-descriptor digests, deadline and policy-decision time
checks, mutation-JTI replay rejection, and stale-fencing rejection. Admission
must finish before repository or driver access. Route handlers may return a
bounded not-implemented result after successful admission; they must not start
P1.2 lifecycle work.

### P1.1d: admission release gate

Run the applicable locked Contract security cases for every protected
operation, including substitution, expiry, replay, and stale-fencing matrices.
Record reproducible evidence and close P1.1 only when the architecture release
gate passes. Any lifecycle/conformance cases that require P1.2 remain explicitly
not claimed.

## Contract consumption

Local and CI validation receive an explicit source root through
`AGENT_CONTRACT_SOURCE_ROOT` or a command flag. The harness:

1. loads `compatibility/agent-platform/contract.lock.json`;
2. runs the existing Git tree, cleanliness, digest, manifest, and Suite verifier;
3. reads the locked OpenAPI to enumerate its external Provider Schema
   references and rejects projection drift;
4. loads only the referenced Schemas and corresponding examples from the
   verified checkout;
5. never writes to the source root or copies its contents into testdata,
   generated code, build output, or CI artifacts.

Normal unit tests remain runnable without proprietary inputs. Contract
projection tests skip unless the explicit source root is provided; the CI
Contract job always provides it, so a skip cannot satisfy that gate.

## Failure and rollback

- Lock, tree, cleanliness, or digest failure stops Contract reads and fails CI.
- Missing Schema/example mappings or unexpected OpenAPI projection changes fail
  the projection test; they are reviewed as Contract compatibility changes, not
  patched around locally.
- Invalid input is rejected before application, repository, or driver calls.
- A P1.1a rollback removes the new DTO/harness package and CI projection step;
  it does not require data rollback because this slice adds no routes or state.
- A P1.1b rollback disables or removes only the new Provider listener,
  capability service, configuration, and tests. It has no data migration or
  runtime-resource rollback because discovery does not dispatch work. Existing
  `/instances` behavior remains unchanged.
- A P1.1c deployment rollback removes only its protected admission routes or
  selects the previous provider revision for new platform bindings. It must not
  migrate existing runs, mutate Agent Platform truth, or delete Provider-local
  evidence.
- If the locked Contract lacks authority for a required status or behavior,
  stop that affected slice and record the gap. Do not invent private protocol.

## Current unproven boundaries

Passing P1.1a proves that a bounded Go wire projection matches selected locked
Schemas/examples and that its JSON decoder fails closed for the tested input
classes. It does not prove semantic-rule completeness, HTTP routing, mTLS,
token admission, application dispatch, durable idempotency/fencing, lifecycle,
the aggregate `sandbox-core-v1` profile, cross-provider interchangeability,
multi-controller reliability, multi-tenant isolation, deployment, or production
readiness.

P1.1b component tests additionally do not prove that Agent Platform PKI issues,
registers, rotates, or revokes the configured workload identities; that a real
Platform caller can discover this revision end to end; that advertised values
are sufficient for scheduling; or that any lifecycle, exec, terminal, snapshot,
restore, network-policy, or other capability is implemented. A valid mTLS
handshake and Schema-valid response do not close P1.1 or `sandbox-core-v1`.
