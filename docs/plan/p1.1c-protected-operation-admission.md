## Purpose and authority

P1.1c establishes a closed, fail-closed admission boundary for every protected
Sandbox Provider operation before any application, repository, or driver work.
It refines P1.1 in [`docs/architecture.md`](../architecture.md) and the parent
[P1.1 plan](p1.1-provider-api-admission.md).

Authority is ordered as follows:

1. the locked local OpenAPI, Schemas, semantic rules, fixtures, and Provider
   Suite in the repository-owned Contract tree;
2. ADR 0001 and `docs/architecture.md`;
3. the parent P1.1 plan;
4. this plan; and
5. implementation details.

The Contract is MIT-licensed and is read only from the verified repository
tree. This repository must not generate derived fixtures or alter the lock as
part of P1.1c.

P1.1b capability discovery remains a mTLS-only exception to the OpenAPI root
security requirement. Its `400`/`501` outcomes are authorized by the local
Contract and remain separate from protected-operation error mapping.

## Scope

The locked OpenAPI applies both mTLS and bearer security by default to every
Provider operation other than the capability-discovery override. P1.1c plans an
admission boundary for the protected mutation and read operations declared by
that OpenAPI. It must:

- verify a compact JWS using the locked closed header and claims surface;
- bind the verified bearer caller to the already verified mTLS peer identity
  and the configured immutable Provider revision;
- bind the token to the exact protected operation and its declared request
  Contract ID and digest profile;
- calculate and compare the normalized request or read-descriptor digest using
  the locked canonicalization rule, without accepting an alternate profile;
- reject invalid issuance, not-before, expiry, deadline, and policy-decision
  time relationships using an injected clock;
- reject a replayed mutation JTI and a stale operation/attempt/fencing tuple
  before dispatch; and
- keep every not-yet-implemented protected route absent until its admission
  preconditions and Contract-authorized response mapping exist.

P1.1c may later expose a bounded, Contract-authorized not-implemented outcome
only after successful admission. It must not create a sandbox, operation,
lease, event, retained result, reconciliation record, or driver call. Those
belong to P1.2 or later.

## Non-goals

This slice does not:

- add P1.2 asynchronous lifecycle, operation-ledger, lease, event, generation,
  reconciliation, or provider-local execution behavior;
- change the local `/instances` API, its Gin router, its DTOs, or its error
  envelope;
- weaken the existing mTLS listener, accept a bearer without verified mTLS, or
  infer caller identity from an unverified header;
- introduce remote key discovery, implicit key rotation, a mutable trust store,
  or an unaudited development bypass;
- advertise `sandbox.exec`, sessions, snapshots, restore, or another runtime
  capability;
- claim aggregate lifecycle conformance or external caller end-to-end compatibility,
  multi-controller reliability, multi-tenant security, deployment readiness,
  or production readiness; or
- redefine P1.1b discovery behavior or its separately authorized error mapping.

## Required decisions before behavior changes

The local Contract defines wire inputs and bindings, but it does not select
this deployment's trust-material distribution, local caller-identity selection
rule, or provider-local retention semantics. Before the first admission-code
commit, a scoped security ADR must make the following local choices explicit
without changing the Contract:

1. a fail-closed, bounded source of trusted verification keys keyed by the
   locked JWS header identifier, including reload and rotation behavior;
2. how one verified mTLS URI SAN is selected when a certificate presents more
   than one configured identity, and how that selected value binds to the
   bearer caller claim;
3. the bounded persistence and expiry semantics for mutation-JTI replay and
   high-water fencing observations across process restart, without creating a
   P1.2 operation ledger; and
4. the exact, operation-authorized error mapping for each admission rejection,
   including precedence when more than one input is invalid.

The ADR must stop rather than invent a response if the locked operation does
not authorize one. It must preserve the P1.1b gap as a separate issue.

## Target boundary

The intended dependency direction is:

```text
providerapi transport -> provider admission application port -> replay/fencing ports
                                                     \
                                                      -> trusted-key and clock ports
```

The admission application package must not import Gin, `instance`, repository
implementations, or drivers. It receives normalized request metadata and
verified TLS peer facts from transport, returns a safe admission decision, and
does not retain raw bearer values, certificates, request bodies, backend IDs,
or secrets in its public result or errors.

Transport owns bounded header/body reading, bearer extraction, TLS context
extraction, and only Contract-authorized response encoding. It may not call an
application, repository, or driver port until admission succeeds. Replay and
fencing ports expose only the atomic comparison needed for admission; they do
not become caller business truth or a Provider lifecycle ledger.

## Delivery sequence

### P1.1c.0: plan and authority inventory

This commit records scope, non-goals, required local decisions, and evidence
boundaries. It updates execution status to planning in progress. No Go behavior
changes in this unit.

### P1.1c.1a: security ADR

[ADR 0002](../adr/0002-provider-operation-admission.md) selects a
startup-frozen local public-key bundle, unique token-subject to verified mTLS
URI SAN binding, injected clock, durable single-controller admission guard, and
operation-authorized `401`/`403`/`409` precedence. It adds no Go behavior or
protected route.

### P1.1c.1b: admission interfaces

Add pure application-port interfaces for trusted-key lookup, clock, replay, and
fencing comparison. No protected route is registered. Tests must prove no
implicit trust source, no mutable global clock, and no driver or repository
dependency.

### P1.1c.2: closed JWS and claim validation

Implement a bounded parser and verifier with closed header/algorithm/claim
allowlists and the ADR-selected key source. Validate Provider revision, caller,
operation, sandbox, operation/attempt, tenant/work order, policy digest, and
request-contract binding exactly as required by the verified Contract input.
All parse, signature, key, and claim failures fail closed before dispatch.

### P1.1c.3: canonical digest and temporal binding

Implement the locked normalized request and read-descriptor digest checks with
the declared digest profile, plus issuance, not-before, expiry, deadline, and
policy-decision time checks. Tests use generated local inputs and never store
or copy local fixtures into generated test data.

### P1.1c.4a: durable single-controller mutation guard

Implement the ADR-selected bounded replay and fencing port as an independent
file adapter. It holds an exclusive local lock for its lifetime and atomically
replaces a versioned `0600` state document. The document retains only JTI and
scope fingerprints, expiry, and the high-water fencing token scoped to one
Provider revision, sandbox, and operation; it never records raw JTI/bearer
values, request bodies, Provider responses, attempt identifiers, lifecycle
state, events, or caller truth. Expired state is pruned on open and
reservation. Lock, recovery, validation, capacity, clock, or write uncertainty
returns an error for fail-closed composition. This is single-controller
component evidence only.

### P1.1c.4b.1: protected-operation application gate

Compose the closed JWS verifier, exact token binding, and mutation guard into
one pure application gate. The compact bearer and bounded request/read
descriptor are transient input only; the result contains neither bearer/JTI/key
data nor Provider-local state. The gate itself verifies the exact RFC 8785
digest after token binding. A token parse/signature failure is classified as
unauthenticated, a verified binding/digest failure as forbidden, a
replay/stale-fencing result as conflict, and an indeterminate guard result as
unavailable. It accepts transport-verified caller and normalized request facts
but does not parse HTTP, load configuration, or register a route.

### P1.1c.4b.2a: shared protected-request facts

Use the same frozen mTLS identity selector in the TLS handshake and future
protected HTTP layer. A client leaf may contain several URI SANs only when
exactly one matches the configured allowlist; none or more than one matching
identity fails closed. The private extractor also accepts exactly one bounded
`Authorization: Bearer` compact value and never returns a public error with
that value. It registers no route and does not yet call the application gate.

### P1.1c.4b.2b.1: frozen trusted public keys

Add a pure, bounded immutable `kid`-to-public-key source for exactly the
ADR-selected `EdDSA` and `ES256` algorithms. It must clone configured key
material at construction and on lookup, reject duplicate IDs and
algorithm/key-type mismatches, and honor cancelled lookup contexts. Reading an
operator file and attaching it to a protected listener remain separate work;
this unit neither loads configuration nor registers a route.

### P1.1c.4b.2b.2: operator public-key file adapter

Read each configured verification key once through a bounded regular-file
adapter. Accept exactly one unencrypted SPKI `PUBLIC KEY` PEM block per file,
then pass the parsed key into the frozen application source. The adapter must
reject absent, non-regular, oversized, malformed, multi-block, or trailing-data
files without blocking on a FIFO. It adds no configuration field, key refresh,
private key, listener, or route.

### P1.1c.4b.2b.3: protected transport composition

Add protected transport composition only after it can prove every rejection,
including a guard error, occurs before a repository or driver spy. Any route
added in this step may return only its Contract-authorized bounded result after
successful admission; it must not dispatch P1.2 lifecycle work.

The local Contract now supplies the authoritative Admission Context carrier.
The feature-branch implementation authenticates the compact bearer before
examining Context or request-document input, then decodes Context strictly,
requires exactly one header value, binds its controller subject to the verified
mTLS URI SAN, checks concrete path and closed canonical query input, verifies
the v2 JWS Context binding and request/read digest, and invokes the pure gate
before any later dispatch. The protected listener reserves an aggregate header
budget for the bounded Context and bearer values. Safe admission errors carry a
generated trace identifier; retryable 503 outcomes carry `Retry-After: 1`. All
14 OpenAPI protected paths are matched. Successful admission still stops at a
bounded Contract-safe unavailable/error result because operation execution is
outside P1.1c.

### P1.1c.4b.2b.4: protected-admission configuration and composition

Keep protected admission independently default-disabled under
`server.provider.protected_admission`. Enabling it requires 1..32 unique,
operator-managed public-key file declarations, each with a closed `EdDSA` or
`ES256` algorithm choice, plus a non-empty durable guard state path. The
configuration layer rejects partial, duplicate, oversized, unsupported, or
blank declarations before the command composition root starts a listener.

The command composition root maps those declarations into the bounded SPKI
file adapter, opens the exclusive single-controller guard, constructs
`ProtectedTransportOptions`, and releases the guard when service startup later
fails or the process exits. Missing, unreadable, malformed, algorithm-mismatched,
or concurrently locked state fails closed; no fallback key, development bypass,
or partially protected listener is permitted. A disabled protected-admission
section leaves the separate mTLS capability-discovery listener unchanged.

This unit adds neither a lifecycle dispatcher nor P1.2 state. The Provider must
not synthesize Context from bearer claims or add a Provider-local lifecycle
cache.

## Failure, rollback, and stop conditions

- A lock, tree, digest, Schema, semantic-rule, or Suite mismatch stops work;
  local code must not patch around it.
- Missing key material, an ambiguous mTLS caller binding, an unavailable replay
  or fencing comparison, or any indeterminate clock decision fails closed and
  prevents route dispatch.
- A missing operation-level response authority stops the affected route rather
  than creating a private error protocol.
- The locked Admission Context carrier is the only accepted admitted-operation
  context source. The token's own claims are not a substitute, and the local
  `/instances` API or a new admission cache must not be used to augment or
  replace it.
- Rollback removes only the P1.1c admission composition from new provider
bindings. It must not alter caller truth, mutate existing runs, or
  delete provider-local evidence.

## Unproven boundaries

This plan does not establish P1.1 completion, aggregate lifecycle conformance,
external caller end-to-end compatibility, multi-controller reliability,
multi-tenant security, deployment readiness, or production readiness. P1.1b
discovery behavior remains a separate operation and is not covered by the
protected-operation error mapping.
