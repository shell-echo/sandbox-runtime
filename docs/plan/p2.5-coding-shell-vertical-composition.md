## Objective

Compose the already bounded P2 components into one honest, runnable Provider
profile without crossing Agent Platform ownership boundaries or promoting
local evidence to external compatibility.

The P2 release gate remains the architecture gate: a separately supplied caller
must run its coding and shell scenarios against this Provider without backend
endpoint leakage or cross-tenant access. This plan first makes such an E2E
technically possible; it does not replace the independent caller.

## Verified Starting Point

The 2026-08-26 audit established:

- Contract namespace `urn:shell-echo:sandbox-runtime:provider-v1`, revision
  `6f549c222ab5ff5b57ed1a49bd2ac5bb95d3b311`, tree
  `b27453d048a2cd8b90f54008d5c4eac28f38c9cb`, and 35 local Suite cases;
- capability semantics are `zero-or-terminal-only` and forbid non-terminal
  advertisement;
- the command root composes Provider lifecycle only, using a fake lifecycle
  driver;
- exec has Contract/domain/coordinator/ledger evidence but no Provider HTTP
  application dispatch or real executor;
- terminal, Gateway, artifact, usage, and operation-family components exist but
  are not assembled into the command root with real adapters;
- startup advertises empty capability and runtime-profile arrays;
- the stable four-mount Provider runtime exists, while only bounded local
  WebSocket/terminal stream adapters exist; there is no Gateway composition or
  public route; and
- no independently owned caller/platform scenario is runnable.

These are implementation and environment facts, not a conclusion that the
individual P2 component gates failed.

P2.5b has since locked revision
`22a148e2898477790512d5bb742605654ff00ebf`, tree
`1a967c9c6ce9646c8431f6ee48699ec9f406a589`, and 38 local Suite cases. It
permits empty, terminal-only, or atomic exec+terminal advertisements while the
command composition remains empty by default.

## Ownership and Non-goals

The Agent Platform continues to own WorkOrder, Run, tenant/user authorization,
ProviderRevision selection, Artifact publication, billing/accounting, aggregate
operation truth, and public Gateway policy. The Provider owns only local
execution and bounded evidence.

P2.5 does not establish aggregate conformance, distributed authorization,
multi-controller operation, hostile multi-tenant isolation, deployment, or
production readiness. It does not add browser, desktop, snapshot/restore, GPU,
nested-container, or port-forward capabilities. It does not reuse `/instances`
wire DTOs or repository truth.

### P2.5g: artifact and usage vertical

Compose artifact acceptance with a real `/outputs` reader/stager, injected
tenant-binding/active-content/malware checks, retained evidence, usage
collection, and all-family operation aggregation.

Gate: durable accept-before-dispatch, missing/rejected/staged/unknown/expired
states, digest/media/size enforcement, usage correlation and reconciliation,
restart behavior, and absence of publication or billing authority.

Local result: the reviewed worktree based on `33dc5d` adds explicit,
default-disabled development artifact and usage configuration. Artifact
acceptance persists the admitted tenant and synchronizes trusted lifecycle
readiness, generation, lease, and fencing before durable reservation. A
process-owned worker survives request cancellation, stops on shutdown, and
persists uncertain work as `outcome_unknown`; recovery redispatches only safe
accepted work and preserves scanner/repository failures. The Docker reader
confines regular-file reads to the owned running generation beneath `/outputs`.
The stager enforces digest, media type, and size before scanners, supplies
content only on scanner stdin, writes a private atomic copy, and returns an
opaque `ref:staging/*` rather than a path or publication URL. Usage observes
durable exec results and derives only byte-stable wall-time and exec-count
entries with `partial` reconciliation, backed by a versioned, locked, atomic
file repository. The command root composes these applications and includes
artifact operations in lifecycle/exec/artifact aggregation; all enabled state
files must be distinct, and production mode rejects the development adapters.

Focused and full race/shuffle, vet, `go mod verify`, unchanged Contract
verification, the locked 38-case Suite, and diff checks pass. A Docker-tagged
`cmd` vertical using a locally cached digest-pinned Alpine image proves exec
output creation, staged/rejected/missing artifact outcomes, bounded partial
usage, all-family reads, opaque-reference non-disclosure, and artifact/usage
restart recovery. This is same-repository, single-controller development
evidence. P2.5g repository CI `33157119149` passes; external caller, aggregate conformance,
multi-controller, multi-tenant, deployment, publication, billing, and
production gates remain open.

### P2.5h: readiness-derived composition and advertisement

Add explicit configuration and a startup dependency graph for the canonical
profile. An explicitly enabled incomplete profile fails startup. A disabled
profile advertises empty arrays. A successfully enabled profile advertises only
the exact locked capabilities and runtime profile, from an immutable snapshot.

Gate: dependency-absence matrix, config validation, startup/shutdown cleanup,
advertisement-to-route/profile consistency, complete local Suite, full Go
gates, and tagged Docker integration.

Local result: the command root now constructs a deterministic dependency graph
after composing lifecycle, protected admission, exec, usage, terminal,
artifact, and operation-reader applications. `coding_shell_enabled` remains
default-disabled; when enabled, any missing admission, lifecycle, runtime,
exec, usage, terminal data-plane, caller-owned Gateway, artifact/evidence, or
aggregation node returns a startup error after releasing all opened state
files. A complete readiness graph projects only the locked
`sandbox.exec@1.0.0`/`exec-v1` and `sandbox.terminal@1.0.0`/`terminal-v1`
capabilities plus `sandbox-runtime-coding-shell-v1` (`container`,
`sandbox-runtime-coding-shell`, `amd64`) from the immutable capability source.
The canonical terminal IDs are used by the development configuration and
fixtures. Config and per-node dependency-absence tests, full race/shuffle,
vet, module verification, the 38-case Suite, fixed-digest Docker integration,
and diff checks pass locally. The command root deliberately does not compose a
caller-owned Gateway/WebSocket edge, so this is component/Contract projection
evidence only; no runnable nonempty-profile deployment or external-caller E2E
is claimed.
