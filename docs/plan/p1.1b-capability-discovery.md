# P1.1b mTLS Capability Discovery Plan

Status: implemented and verified on `main`. The strict discovery HTTP
input-boundary hardening merged through PR #8, and both its PR and post-merge
CI runs passed. This plan defines intended scope and acceptance criteria;
implementation and validation evidence remains authoritative in
[`docs/STATUS.md`](../STATUS.md).

## Baseline and authority

This plan refines only P1.1b of the
[Provider API admission plan](p1.1-provider-api-admission.md). Its repository
baseline is `main` at revision `255c927`, where P1.1a is merged and the P1.1
release gate remains open.

Authority, in descending order, is:

1. the locked upstream OpenAPI, JSON Schemas, semantic rules, examples, and
   Conformance Suite at revision
   `0c91871fa469e951b8a508fe735a2a9a5797a67e`;
2. ADR 0001 and [`docs/architecture.md`](../architecture.md);

private extension.

## Outcome and scope

P1.1b adds one independently deployable, default-disabled Provider HTTPS
listener. After a client certificate passes both normal CA verification and an
exact URI SAN allowlist, the listener serves one operation:

```http
GET /v1/capabilities
```

The successful response is the raw Sandbox Provider API v1 capability document.
It is not wrapped in the local management API response envelope. The document is
an immutable startup snapshot obtained through an application port, explicitly
mapped into `providerapi/v1` wire DTOs, validated, and encoded before the
listener accepts traffic.

The process continues to host the existing local management API on its own
listener. Failure to configure, load, bind, or serve the enabled Provider
listener is a process-level startup failure: the existing multi-server
lifecycle shuts down the other server instead of leaving a partially available
revision.

## Non-goals

This slice does not:

- add any sandbox, operation, event, exec, session, snapshot, restore, lease, or
  termination route;
- add a mutation placeholder, not-implemented mutation handler, or request-body
  admission path;
- implement JWS, bearer-token validation, replay protection, fencing, request
  digests, or P1.1c policy;
- dispatch to `instance.Service`, a repository, a runtime driver, or Docker;
- alter `/health`, `/instances`, the local management listener, or its response
  envelope;
- implement lifecycle, durable operations, reconciliation, certificate
  rotation, dynamic capability changes, or hot configuration reload;
- advertise `sandbox.exec`, `sandbox.terminal`, lifecycle compatibility, or any
  other capability that the current Provider revision has not implemented and
  passed through its required gate;
- claim `sandbox-core-v1` conformance, Agent Platform compatibility,
  multi-tenant safety, deployment readiness, or production readiness.

## Listener and configuration contract

The Provider listener is a sibling of `server.api`, not a route group within
it. Its built-in state is disabled. Enabling it requires a complete validated
configuration; there is no plaintext or authentication-optional fallback in
development or production.

Transport configuration contains:

- an explicit enabled flag and a dedicated host and port whose port differs
  from `server.api.port`;
- server certificate and private-key file paths;
- a client CA bundle file path;
- an allowlist of 1..32 exact fragment-free client URI SAN identities, each
  containing 1..2048 valid UTF-8 bytes;
- TLS minimum version 1.2.

The implementation must use `tls.RequireAndVerifyClientCert` with the configured
client CA pool. Normal certificate chain, validity period, and client-auth EKU
verification run before the URI identity check. The admitted identity is an
exact URI SAN from the verified leaf certificate:

- Common Name is never consulted or accepted as a fallback;
- DNS, email, and IP SANs do not satisfy the identity allowlist;
- allowlist entries are validated as absolute URI identities and compared in a
  single documented canonical representation;
- no URI scheme, including `spiffe`, is hardcoded by the service;
- a certificate signed by the configured CA but lacking an exact allowed URI
  SAN is rejected during the TLS handshake, before HTTP routing.

Server certificate, private key, client CA, and identity allowlist are loaded
and frozen once during startup before the listener accepts connections. Missing,
empty, unreadable, malformed, mismatched, or semantically invalid TLS material
fails startup. The server certificate and private-key files are each limited to
64 KiB. The client CA bundle is limited to 256 KiB and 32 CA certificates.
Every TLS path must resolve to a regular file. Certificate rotation and reload
are intentionally deferred.

Application capability configuration is separate from transport configuration.
It requires:

- an explicit, nonempty Provider revision ID;
- explicit positive values for every required Provider limit;
- a positive workspace-byte limit when present;
- a nonnegative GPU-count limit when present, where zero explicitly describes
  no GPU capacity and omission means the limit is not declared;
- one nonempty, content-addressed compatibility-profile entry satisfying the
  locked capability Schema, including its required suite identity, version,
  level, and `sha256` digest.

The enabled Provider listener must not infer a revision ID or hard limit from a
mutable runtime observation. Invalid application capability configuration fails
before traffic is accepted. Disabled configuration starts no Provider listener
and makes no Provider route reachable.

## Honest initial capability document

The P1.1b startup snapshot intentionally advertises:

- `api_version: "v1"`;
- the explicitly configured Provider revision ID and field-valid hard limits;
- an empty `capabilities` array;
- an empty `runtime_profiles` array;
- the Contract-required nonempty content-addressed compatibility-profile
  metadata.

The compatibility-profile entry is descriptive compatibility metadata required
by the locked Schema. It does not itself authorize scheduling or claim runtime
support. A feature is schedulable only when its capability ID and applicable
runtime profile are explicitly advertised. In particular, the presence of a
snapshot/restore compatibility-profile document does not advertise
`sandbox.snapshot.*` or `sandbox.restore`; those capability IDs remain absent.

This conservative document reflects the present implementation: the local
`/instances` lifecycle is not Provider API lifecycle, and no Provider
capability has completed its conformance gate. Future slices may add capability
and runtime-profile entries only with their own implementation and evidence.

## Package and dependency boundaries

Implementation stays within these boundaries:

```text
cmd composition root
    |-- local server/api --------------------> instance application service
    `-- providerapi HTTP/TLS adapter --------> provider capability port
              |                                      |
              `--> providerapi/v1 wire DTOs          `--> immutable app model
```

Expected implementation areas are:

- `provider/`: application-owned capability model, validation rules, focused
  read port, and immutable static snapshot implementation. It imports neither
  HTTP/TLS/Gin nor `providerapi/v1`, `instance`, repositories, or drivers.
- `providerapi/v1/`: wire DTO validation needed to fail closed when constructing
  a capability response. It remains transport-only and does not become an
  application or persistence model.
- `providerapi/`: Provider HTTP server, exact route registration, mTLS identity
  admission, application-to-v1 mapper, safe error response behavior, and raw
  JSON encoding. It may import `provider` and `providerapi/v1`; the reverse
  dependencies are forbidden.
- `config/`: distinct Provider listener/TLS settings and application capability
  settings, with typed validation and environment bindings. Configuration
  structs must not leak into application or transport APIs.
- `cmd/serve.go`: the composition root maps validated configuration into the
  application snapshot and Provider server, then adds the enabled server under
  a distinct name to the existing `server.RunE` set.
- `config.tpl.toml`: documents the disabled default and every required setting
  without embedding working credentials or a claim of enabled capability.
- `.github/workflows/ci.yml`: only the narrow adjustment, if required, that
  makes the locked-schema test for the emitted P1.1b response mandatory rather
  than skippable in the Contract job.

The existing `server.Server` and `server.RunE` lifecycle are reused. The local
`server/api`, `server/api/router`, `instance`, repository, and driver packages
must not be modified for this slice. No broad server refactor is permitted.

The application port returns an application-owned snapshot, not a v1 DTO. The
Provider adapter performs an explicit field-by-field mapping. The source owns
defensive copies of all slices and pointer values, and callers cannot mutate its
stored state. The adapter validates the mapped v1 document and pre-encodes or
otherwise freezes a successful representation before serving. Repeated reads
therefore cannot observe later mutation of configuration or source values.

## HTTP behavior

The Provider router registers only the exact GET operation. A successful
response has:

- status `200`;
- Contract-compatible `Content-Type: application/json`;
- a raw `providerapi/v1.Capabilities` JSON document;
- no local `{code,message,success,data,time,latency}` envelope;
- no backend identifiers, paths, endpoints, daemon details, credentials, or
  certificate contents.

`HEAD /v1/capabilities` and every other method on that path are rejected with
`405`; HEAD must not be implicitly served as GET. Unknown paths return `404`.
All other Provider API routes remain unregistered and therefore return `404`.

Discovery does not parse, require, validate, or derive authority from an
`Authorization` header. An otherwise admitted mTLS caller receives the same
result whether that header is absent or contains an arbitrary bearer value. A
bearer value without an admitted client certificate cannot reach HTTP handling.

The endpoint has no query parameters or request document. For metadata that
reaches the handler, a nonempty query string (including a bare trailing `?`),
nonzero or unknown `Content-Length`, and `chunked` transfer encoding receive an
empty `400` response before capability, application, repository, or driver
dispatch. The handler makes that decision from request metadata only and does
not read or probe `Body`. This is a handler-level property: it does not claim
that the Go server lifecycle or standard library never reads or drains request
framing. A zero-length request remains valid.

Unsupported transfer codings are parser-level behavior, not handler behavior.
The real mTLS HTTP/1.1 server test under the project Go 1.26 toolchain observes
`Transfer-Encoding: gzip` receiving the standard-library `501` response before
the handler runs. It deliberately makes no assertion for HTTP/2 or other Go
versions. The locked OpenAPI declares no parameters or request body for this
operation, and its operation-level response list includes neither `400` nor
`501`. Its generic malformed-request component is not operation-level wire
authority. The empty handler `400` and parser-level `501` therefore remain
fail-closed transport observations rather than fully path-authorized Provider
error documents. Upstream clarification is required before adding a documented
error payload or broader rejection behavior. No hidden mutation route or
parser is added merely to exercise these cases.

## Response validation and Contract evidence

Local validation must reject a capability document before startup when any
required value is missing, any required limit is not positive, a configured
workspace-byte limit is not positive, a configured GPU-count limit is negative,
an enum or digest is invalid, identifiers or versions violate the locked
constraints, entries conflict or duplicate one another, or the honest
zero-capability policy is violated. A configured GPU count of zero is valid.

This local validator is a fail-closed construction boundary, not a substitute
for the proprietary JSON Schema. The Contract test must:

1. verify the local lock and clean read-only Contract tree before reading it;
2. map the actual application startup snapshot into the v1 response;
3. encode the same representation served by the HTTP handler;
4. validate those bytes against `sandbox-capabilities.schema.json` from the
   locked checkout;
5. retain all P1.1a projection, fixture, decoder, enum, and identifier
   regressions.

A skipped Contract projection test is not evidence. CI must supply the explicit
source root and execute the emitted-response projection test in its mandatory
Contract job.

## Test and acceptance matrix

The original P1.1b acceptance record remains the 2026-08-01 CI run documented
in `docs/STATUS.md`. The additional port, TLS material, CA count, and URI
allowlist bounds below are post-closure hardening; local gates are necessary but
do not replace CI evidence for their committed revision.

### Configuration and construction

- the default configuration leaves the Provider listener disabled;
- a fully specified enabled configuration loads from TOML and environment
  overrides without changing local API settings;
- enabled configuration rejects reuse of the local API port, even when the
  configured host strings differ;
- enabled configuration rejects missing or invalid address, revision, required
  limit, compatibility profile, certificate, key, client CA, or URI allowlist;
- zero/negative required limits, a zero/negative workspace-byte limit, and a
  negative GPU-count limit fail closed, while a zero GPU-count limit is
  accepted; malformed digest, duplicate/conflicting profile data, relative or
  malformed URI identities, empty identity entries, and a certificate/key
  mismatch fail closed;
- maximum-sized valid TLS files, a 32-certificate client CA bundle, a 32-entry
  identity allowlist, and a 2048-byte identity are accepted; exceeding any
  boundary by one fails closed;
- disabled mode creates no Provider server; enabled mode adds exactly one
  separately named server to the lifecycle set;
- a Provider bind, TLS-load, or serve failure shuts down the process's other
  server through the existing fail-together lifecycle.

### TLS and identity admission

Use generated, test-local certificate hierarchies and a real TLS socket:

- a valid CA-signed client certificate with client-auth EKU and an exactly
  allowed URI SAN completes the handshake and receives `200`;
- no client certificate, an untrusted chain, an expired/not-yet-valid
  certificate, or the wrong EKU fails the handshake;
- a trusted client certificate with no URI SAN or only a non-allowed URI SAN
  fails the handshake;
- Common Name, DNS SAN, email SAN, and IP SAN cannot substitute for the allowed
  URI SAN;
- one exact allowed URI among multiple URI SANs is admitted;
- plaintext HTTP on the Provider port fails;
- a bearer header without a valid certificate never reaches the handler;
- valid admitted mTLS succeeds with no bearer and with an arbitrary bearer,
  producing the same capability document.

### HTTP, immutability, and absence

- exact GET returns raw, valid JSON with the expected status and content type;
- the response contains the configured revision and field-valid limits,
  including an accepted zero GPU count when configured, zero capabilities, zero
  runtime profiles, and the required content-addressed compatibility profile;
- repeated calls return the same semantic document, and mutation of constructor
  input, retrieved snapshots, or mapper output cannot change later responses;
- invalid application or mapped v1 documents fail before listening;
- HEAD and every non-GET method on `/v1/capabilities` return `405` without
  invoking the capability source;
- a real mTLS HTTP/1.1 server distinguishes handler-visible bare trailing `?`,
  unknown query, nonzero `Content-Length`, and chunked nonempty bodies (empty
  `400`, with no capability-source read after construction) from unsupported
  transfer coding (the Go parser's `501` before the handler); the test does not
  generalize parser behavior to HTTP/2 or other Go versions;
- handler rejection does not read or probe `Body`; any server-level draining is
  outside this handler-level claim; a zero-length GET remains `200`;
- unknown paths return `404` without invoking the source;
- every Provider mutation path listed in `docs/architecture.md`, plus status,
  operation, result, manifest, and event-read paths, is absent and returns `404`;
- absence tests use spies to prove no instance service, repository, or driver
  dispatch occurs;
- the existing local `/health` and `/instances` router tests remain unchanged
  and passing.

## Exit criterion and evidence language

P1.1b may be marked implemented only when the configuration, real-handshake,
route-absence, immutability, response-validation, race, vet, lock, and mandatory
locked-schema projection tests above pass with reproducible commands. Its
completion proves only mTLS-admitted capability discovery for the exact tested
revision and document.

It does not close P1.1. Token binding, digest substitution, expiry, replay, and
stale-fencing admission remain P1.1c/d requirements. It also does not prove any
runtime capability, lifecycle conformance, multi-controller reliability,
multi-tenant isolation, deployment readiness, or production readiness.

## Rollback

Rollback disables or removes the separate Provider listener and its immutable
capability source while leaving the local management API and instance data
unchanged. Because P1.1b creates no sandboxes, operations, events, sessions,
snapshots, or persistent Provider state, no data migration or cleanup is
required.

If a deployed Provider revision has been registered externally, rollback is
coordinated by selecting the previous revision only for new bindings. Existing
run bindings and Agent Platform truth are not rewritten, and Provider-local
evidence is not deleted. TLS material is removed only through the deployment's
credential-management procedure, not by application rollback code.
