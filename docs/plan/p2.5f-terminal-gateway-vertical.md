# P2.5f Terminal and Gateway Vertical Plan

Status: P2.5f0 authority, data-plane, recovery, and deployment audit complete
as design evidence on 2026-08-27. P2.5f1 is the next implementation slice.
No terminal allocator, concrete WebSocket adapter, command composition, or
nonempty capability advertisement is enabled by this plan.

## Objective

Compose the existing terminal-session authority and Gateway components into a
real, restart-aware development vertical without exposing backend endpoints or
taking ownership of caller users, tenants, public authorization, or reconnect
policy.

P2.5f must make these two boundaries work together while keeping them
independent:

- the Provider asynchronously allocates and owns a provider-local terminal
  resource, then returns only an expiring `ref:session:*` handoff; and
- the calling platform Runtime Gateway authorizes a user, resolves that opaque
  reference over a trusted channel, and proxies the terminal stream.

This plan does not change the repository-owned Provider Contract. Contract,
Gateway, deployment, and external-caller evidence remain separate gates.

## Authority and Protocol Boundary

The locked Contract authorizes only:

- `POST /v1/sandboxes/{sandbox_id}/runtime-sessions`; and
- `GET /v1/operations/{operation_id}/runtime-session`.

The handoff schema identifies the protocol as `websocket`, but it does not
define a public Gateway route, an end-user credential, terminal resize, an
explicit close-session mutation, or a browser/desktop/port-forward protocol.
Those features must not be inferred from local interfaces.

The Provider may persist only provider-local allocation and recovery evidence.
The calling platform remains authoritative for caller identity, tenant policy,
Gateway grants, public routing, revocation policy, and recording policy. No
default or static allow-all authorizer is acceptable for an enabled Gateway.

## Verified Starting Point

| Area | Verified implementation fact | Missing evidence or behavior |
| --- | --- | --- |
| Provider transport | Protected open and handoff routes exist and enforce strict preflight and opaque projection | The command root injects no session application |
| Session application | `Open` durably reserves through `Authority`; `GetHandoff` reads successful evidence | It deliberately does not allocate, dispatch, or reconcile a terminal |
| Session repository v1 | File and memory adapters persist sessions, idempotency, and manually supplied sandbox authority | No allocation receipt, runtime observation, or lifecycle-to-session authority synchronization |
| Gateway | Injected `Authorizer`, `ReferenceResolver`, `RevocationSource`, and `Recorder` support bounded reconnect, expiry, revocation interruption, bidirectional frames, and metadata-only audit | No HTTP/WebSocket wire adapter, deployable composition, or caller-owned production ports |
| Docker exec | P2.5e creates non-TTY execs with stdout/stderr capture and no stdin | No PTY, stdin, resize, terminal allocator, or reconnectable stream |

| Dependencies | No WebSocket implementation is selected in `go.mod` | A maintained library and its wire limits must be reviewed in P2.5f4 |

These facts are component and source evidence. They do not establish a
terminal vertical, external caller E2E, tenancy, deployment, or production
readiness.

## Rejected Shortcut: Reusing Docker Exec Attach

The P2.5e executor is not a terminal transport. It creates a Docker exec with
`TTY: false`, does not attach stdin, and retains only a process-local hijacked
stdout/stderr reader while capture is active.

Docker exec start/attach is a one-shot stream lifecycle. The current adapter
cannot reconstruct its lost stream after the Provider process restarts, and a
new shell process would be a different terminal rather than a reconnection to
the accepted runtime session. Persisting the backend exec ID does not make the
stream reconnectable.

Therefore P2.5f must first introduce a genuinely reconnectable terminal
mechanism, such as a guest-side terminal broker/session manager or an
equivalent design with independently attachable state. A test fake, a retained
Go closure, or a newly created shell on every reconnect cannot satisfy the
restart/reconnect gate.

## Data-Plane Decision

The implementation must use focused ports with inward-pointing dependencies:

```text
Provider session transport
          |
          v
durable session coordinator
          |
          +--> terminal runtime port --> Docker terminal adapter --> guest broker
          |
          +--> opaque reference registry

caller-owned WebSocket adapter --> Gateway --> reference resolver --> fresh broker dial
                                  |  |  |
                                  |  |  +--> caller-owned audit recorder
                                  |  +-----> caller-owned revocation source
                                  +--------> caller-owned authorizer
```

The terminal runtime port owns allocation, observation, attachment, and cleanup
of a terminal resource. It returns backend-neutral allocation evidence to the
session coordinator. Backend container IDs, broker socket paths, network
addresses, credentials, and transport handles remain private to the Docker
adapter.

The opaque reference registry binds one `ref:session:*` value to the exact
sandbox, runtime-session, connection generation, expiry, and private adapter
identity. A resolver validates those fields on every connect and reconnect,
then constructs a fresh dial operation. A Go closure is runtime state, not
durable state, and must never be serialized.

## Persistence and Recovery

P2.5f2 introduces a backward-compatible session repository migration. The
provider-neutral session record may add:

- an immutable allocation receipt;
- opaque reference and connection generation;
- allocation and observation timestamps; and
- expiry and cleanup state needed for deterministic recovery.

The Docker adapter owns a separate private state record containing the backend
terminal/broker identity needed to observe and reattach. Provider API DTOs and
the session authority repository must not contain that private identity.

The coordinator follows durable accept-before-allocation:

1. Validate Contract and protected admission before application dispatch.
2. Atomically reserve the accepted session request and sandbox authority.
3. Allocate once or reconcile an existing private receipt.
4. Persist running state and the exact allocation receipt.
5. Register the opaque reference and connection generation.
6. Recheck sandbox authority transactionally before committing success and
   minting the handoff.

On startup, accepted and running records are reconciled against private adapter
state. Known absence may become a bounded terminal failure. Uncertain outcome
must remain `outcome_unknown`; it must not allocate a replacement terminal or
mint a handoff. A succeeded, unexpired session is reconnectable only when the
same broker identity can be reconstructed and observed.

Session authority must be derived from trusted lifecycle application state.
Tests may use direct repository setup, but command composition must not depend
on operators or handlers manually calling `PutSandboxAuthority`.

## Lifetime, Cleanup, and Capacity

The current Contract has no close-session route. Gateway grant revocation
interrupts the authorized proxy connection; it does not by itself authorize a
Provider session mutation or prove that the terminal process was removed.

The Provider must clean up terminal resources when their handoff expires, when
the owning sandbox is removed or becomes invalid, and during bounded shutdown
or startup reconciliation. Cleanup must be idempotent and identity-bound so it
cannot remove a foreign or replacement resource.

Configuration must bound at least:

- concurrent terminals per controller and per sandbox;
- terminal lifetime, reconnect attempts, and reconnect backoff;
- WebSocket frame and message sizes, read/write deadlines, and queued bytes;
- broker attach attempts and operation timeouts; and
- shutdown cleanup duration.

An explicit close-session API, resize messages, keepalive semantics beyond
standard WebSocket control frames, and session replacement require separate
protocol authority. They are excluded from this plan unless the relevant
Contract or caller-owned Gateway protocol is reviewed and locked first.

## Delivery Slices

### P2.5f0: authority, data-plane, recovery, and deployment audit

Record the verified gaps, reject one-shot Docker exec attach as restart
evidence, define ownership and persistence boundaries, and split the vertical
into reviewable implementation slices.

Gate: documentation review and `git diff --check`. This is design evidence
only.

### P2.5f1: reconnectable terminal runtime port and Docker adapter

Define provider-neutral allocate, observe, attach, and cleanup contracts. Add a
Docker development adapter backed by a genuinely reconnectable terminal
mechanism. Keep all backend identity in adapter-private durable state.

Gate: focused PTY/stdin/output, context cancellation, identity conflict,
capacity, expiry, cleanup, provider-restart reattach, sandbox-removal, and real
Docker integration tests. Resize remains excluded.

### P2.5f2: durable session coordination and repository migration

Extend the session application with accept-before-allocation dispatch,
receipt attachment, observation, reconciliation, and lifecycle authority
synchronization. Migrate v1 session files without losing accepted operations
or opaque handoff evidence.

Gate: idempotent replay/conflict, allocation lost-response, no duplicate
allocation, generation/fencing, restart, outcome-unknown, expiry, corruption,
and lifecycle-authority matrices.

### P2.5f3: opaque reference registry and resolver

Persist an identity-bound reference record and resolve it into a fresh adapter
dial on every connection attempt. Reject unknown, expired, revoked, wrong-
generation, and mismatched session references without exposing backend data.

Gate: restart reconstruction, generation fencing, reference collision,
expiry, revocation, no-backend-leakage, and concurrent resolve/cleanup tests.

### P2.5f4: WebSocket and terminal stream adapters

Select a maintained WebSocket library and adapt bounded client frames and the
backend terminal byte stream to `gateway.Stream`. Enforce origin/authentication
policy at the caller-owned edge, frame/message bounds, deadlines, close
behavior, and cancellation.

Gate: bidirectional binary data, control frames, oversized input, slow reader
and writer, abrupt disconnect, cancellation, race, and dependency/security
review. This slice does not provide an authorizer.

### P2.5f5: Gateway composition

Compose the existing Gateway only when a caller-owned `Authorizer`,
`RevocationSource`, and `Recorder`, plus the Provider-backed resolver and both
wire adapters, are supplied. Missing dependencies fail startup or leave the
Gateway disabled; no allow-all fallback is permitted.

Gate: authorization binding, cross-tenant denial, expiry, revocation
interruption, fresh resolution on reconnect, reconnect exhaustion,
metadata-only audit, and failure-closed dependency matrices.

### P2.5f6: command configuration and process lifecycle

Add explicit development configuration, startup recovery order, capacity
limits, and shutdown cleanup. Inject the session application into Provider
transport only after recovery succeeds. Continue to reject the development
terminal/Gateway composition in production mode.

Gate: config validation, disabled/incomplete/enabled startup matrices,
repository locking, startup reconciliation, shutdown ordering, and route
nondisclosure. Capability advertisement remains empty until P2.5h.

### P2.5f7: terminal vertical evidence gate

Run focused race/fault matrices, full race/shuffle, vet, unchanged Contract
verification, the locked 38-case Suite, dependency-boundary checks, and live
Docker integration. Record repository CI separately.

This gate closes only the single-controller development terminal/Gateway
vertical. Independent caller E2E remains P2.5i. Aggregate conformance,
multi-controller reliability, hostile multi-tenant security, deployment, and
production readiness remain open.

## Required Validation

All Go slices require:

```bash
go test -race -shuffle=on -count=1 ./...
go vet ./...
```

Provider transport or Contract projection changes also require:

```bash
go run ./cmd/verify-contract -source-root .
go run ./cmd/run-conformance -source-root . -race -shuffle
```

Docker terminal behavior requires a named live integration target added to the
repository Docker integration workflow. The exact command must be recorded
when P2.5f1 introduces that package; the existing lifecycle/exec command alone
does not exercise a terminal broker.

## Non-goals and Evidence Boundary

P2.5f does not add or prove:

- a new Provider Contract route or aggregate conformance;
- platform user, tenant, grant, or public Gateway authority;
- explicit close-session or resize protocol semantics;
- distributed revocation or multi-controller persistence;
- hostile multi-tenant isolation;
- a deployable production topology; or
- an independently owned caller/platform E2E.

P2.5f0 is complete when this audit is reviewed and committed. P2.5f1 is the
next implementation step; P2.5g, P2.5h, and P2.5i remain ordered after the
terminal vertical.
